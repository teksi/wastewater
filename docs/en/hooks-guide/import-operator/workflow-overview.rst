Workflow Overview
=================

The import workflow transforms source data into canonical TWW changes without
directly modifying the live TWW schema.

Processing stages
-----------------

The workflow runs through the following stages:

.. code-block:: text

   XTF source
       |
       v
   quarantine import with ili2pg
       |
       v
   quarantine validation
       |
       v
   source-model mapping
       |
       v
   canonical effect projection
       |
       v
   effect overlay
       |
       v
   row-level change construction
       |
       v
   validation and rights classification
       |
       v
   review-feature generation
       |
       v
   prepared source or pending review job

Quarantine schema
-----------------

The source XTF is first imported into a quarantine schema populated by ili2pg.

The quarantine schema:

* contains the physical tables generated by ili2pg;
* retains source-model class and attribute names;
* may use joined-table inheritance;
* contains source object identities and physical foreign keys;
* is not the canonical TWW model;
* is not written directly into the live TWW schema.

The quarantine schema is validated before projection begins.

Canonical projection
--------------------

After validation, the imported source rows are projected to canonical TWW
effects.

Canonical effects describe intended outcomes such as:

* update one canonical attribute;
* require a canonical object to exist;
* require a canonical object not to exist.

Effects do not yet state whether an object is inserted, updated or deleted.
That decision is made later by comparing effects with the current live state.

Change construction
-------------------

The workflow compares projected values with current objects in the live
canonical schema.

It constructs row-level changes with:

* canonical class;
* canonical object identifier;
* operation;
* old values;
* new values.

Supported operations are:

``insert``
   The canonical object does not currently exist and will be created.

``update``
   The canonical object exists and one or more values will change.

``delete``
   The canonical object exists and will be removed.

Rights and validation
---------------------

Every change is evaluated against:

* effective rights configuration;
* provider privileges;
* dataowner privileges;
* ownership rules;
* old values;
* new values;
* the row-level operation;
* configured business validations.

A rejected or unauthorized change is retained as an unpermitted change for
review. It is not silently discarded.

Review output
-------------

The final result contains grouped and classified changes.

Typical groups are:

* created objects;
* altered objects;
* deleted objects;
* unpermitted changes.

The workflow may also generate spatial or tabular review features for supported
canonical classes.

Source roles and persistence
----------------------------

Workflow behavior is controlled by the source role and persistence setting.

.. code-block:: text

   source_role = base
   persist_job = false
       -> prepare source only

   source_role = base
   persist_job = true
       -> create pending baseline review job

   source_role = incremental
   persist_job = true
       -> combine with prepared baseline
       -> create pending review job

An incremental source with ``persist_job = false`` is not supported because an
incremental source is expected to finalize the prepared workflow.

Projection modes
----------------

Baseline and incremental sources intentionally use different projection
policies.

Full projection
~~~~~~~~~~~~~~~

A baseline source normally uses full projection.

Full projection may include:

* implicit source mappings;
* explicit source mappings;
* explicit defaults;
* direct attribute mappings;
* function-backed mappings;
* explicit relation roles;
* unambiguous relation discovery.

Explicit-only projection
~~~~~~~~~~~~~~~~~~~~~~~~

An incremental source normally uses explicit-only projection.

Explicit-only projection includes:

* explicitly selected classes;
* explicitly selected attributes;
* applicable explicit defaults;
* function-backed mappings.

Implicit mappings may still supply structural information, but they do not add
unselected attributes to the incremental payload.

This prevents an incremental model from overwriting canonical values merely
because the corresponding source column exists.

Operational invariants
----------------------

The following conditions should hold for every workflow:

* source files are assigned the correct role;
* baseline and incremental sources use the same job identifier;
* the incremental source is compatible with the prepared baseline;
* effective mappings match the source model and language;
* canonical metadata matches the live TWW release;
* rights cover all canonical classes produced by the workflow;
* the provider and dataowner context is correct;
* a pending job is created only after successful classification and review
  generation.
